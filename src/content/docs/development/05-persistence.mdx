> **Principle**
>
> Model the persistence layer for **data storage**, not for business logic.
> Persistence is an implementation detail: it is declared once, generated, and kept out of the
> rules.

---

# Goals

These guidelines aim to create a persistence layer that is:

- Simple
- Explicit
- Testable
- Performant
- Free of business logic

The persistence layer never dictates the architecture of the application.

---

# Guiding Principles

## Persistence is an Adapter

```
┌──────────────────────────────┐
│ REST resource      generated │
└──────────────┬───────────────┘
┌──────────────▼───────────────┐
│ Service + rules  hand-written│   the domain: entity, rules, service
└──────────────┬───────────────┘
               │ ReadAccess, CreateAccess, UpdateAccess, DeleteAccess
┌──────────────▼───────────────┐
│ Accesses, mappers  generated │
│ stratastax-persistence       │
│ jOOQ + reactive pg client    │
│ PostgreSQL                   │
└──────────────────────────────┘
```

The rules never know **how** data is stored: they take and return domain values. The service
talks to typed accesses; SQL lives in the generated code and the library underneath it.

There is no ORM. jOOQ builds the SQL, the Vert.x reactive PostgreSQL client runs it, and every
call is a `suspend` function. See [persistence](/technical/components/persistence/).

# One Entity, Declared Once

An entity is a plain Kotlin data class. Its annotations
([stratastax-entity](/technical/components/entity/)) declare how it is stored, exposed and
searched; they carry no behaviour and pull in no framework.

```kotlin
@RestEntity(GameV1::class, GameListV1::class)
@DomainEntity
@PersistenceEntity(GameColumns.TABLE)
data class Game(
    @SearchFilter
    @SearchSort(tiebreaker = true)
    @DomainCreateGenerated
    @PersistenceId
    @PersistenceColumn(GameColumns.PUBLIC_ID)
    val id: GameId,

    @PersistenceVersion
    @PersistenceColumn(GameColumns.VERSION)
    val version: Long,

    @DomainCreate
    @DomainUpdate
    @param:RestProperty("displayName")
    @PersistenceColumn(GameColumns.DISPLAY_NAME)
    val name: String,
)
```

From it, [codegen](/technical/components/codegen/) generates the commands, the row mapper, the REST
mapper and the accesses. The models stay separate where it matters:

| Model | Owned by | Purpose |
|--------|---------|---------|
| DTO (`GameV1`) | the contract, generated by openapi-generator | API contract |
| Entity (`Game`) | the service | Business concepts and rules |
| Table (`GAME`) | the contract's migrations, generated by jOOQ | Database storage |

Neither the DTO nor the jOOQ record ever reaches the rules, and the entity never reaches the API
unmapped. Because the mappings are generated from one declaration, adding a field is one change,
and a column or DTO property that does not match is a build error.

**Rule**

> Declare persistence on the entity; never write it by hand where the generator can.

# Choose the Right Strategy

| Use case | Approach |
|----------|----------|
| Create, read, update, delete with relations | The generated accesses |
| Lists with filters, sorting and paging | `findAll` with a `SearchRequest`, or the query DSL |
| A lighter view (id and name) | A projection: `@DomainEntityProjection` (`GameRef`) |
| Many rows at once | `createAll`, `updateAll`, `deleteAll` |
| A work queue | `FOR UPDATE SKIP LOCKED` reads |
| Reporting, aggregation, statistics | A hand-written jOOQ query in its own read access |
| Importing a file | `persistence-csv`, with the same row mappers |
| Processing a large set | Page through it with the cursor; never load it whole |

**Rule**

> Use the simplest mechanism that solves the problem. Do not force a report through entity
> loading, and do not hand-write what an access already does.

# Repository Responsibilities

Accesses exist to retrieve and persist entities.

Accesses are **not** query engines.

Accesses are **not** business services.

Accesses are **not** report generators.

Good:

```kotlin
override suspend fun getGameSuggestions(query: String): List<GameRef> =
    readAccess
        .findAllGameRef {
            limit = MAX_SUGGESTIONS
            sort { GameEntityModel.fields.name.asc() }
            filter { GameEntityModel.fields.name.containsIgnoreCase(query) }
        }.items
```

Bad:

```kotlin
interface GameRepository {
    fun findGamesByNameAndPlayersAndTagsAndYear(...)
    fun exportGameReport(...)
    fun calculatePopularity(...)
}
```

A question that needs its own SQL gets its own, named read access.

# Relations

Relations are declared, not loaded by hand:

| Relation | Annotation | Read | Write |
|---|---|---|---|
| A reference to another entity | `@PersistenceJoinOne` | Joined in the same query | The foreign key |
| Children owned by the entity | `@PersistenceJoinMany` + `@PersistenceManageChildren` | A JSON array in the same query | Created, updated and deleted with the parent |
| Many-to-many links | `@PersistenceJoinManyThrough` + `@PersistenceManageLinks` | A JSON array in the same query | The junction rows only |

Related data comes in one query, so a list of matches with their participants is one round trip,
never one per match.

---

# Versions and Deletes

- **Optimistic locking**: an entity with `@PersistenceVersion` gets its version as `ETag`; every
  update and delete requires the version it read (`If-Match`) and fails when someone changed it
  first.
- **Soft delete** is declared per entity and applied to every read and write, so a deleted row
  never shows up by accident.

# Transactions

Transactions belong to the service.

```kotlin
unitOfWork.transaction {
    val edit = matchEditAccess.findById(editId) ?: throw MatchEditNotFoundException(editId)
    matchUpdateAccess.update(edit.matchId, edit.toUpdate(), version)  // both writes or neither
    matchEditUpdateAccess.update(editId, decided(edit), edit.version)
}
```

`UnitOfWork.transaction { }` is carried by the coroutine, supports propagation, savepoints,
isolation levels and read-only transactions, and the idempotency record of the request joins it, so
a request and its replay record commit together.

Keep transactions:

- short
- explicit
- focused

Never call another service, send a mail or wait on an external system inside a transaction.

---

# The Schema

- Migrations live in [stratastax-contract](/technical/components/contract/), never in the service,
  and follow its naming rules: a private `BIGINT` key and a public UUID, `created_at`/`updated_at`,
  a `version`, named constraints and a comment per table.
- A migration that ran is never changed; a change is a new migration.
- Only the public id leaves the service. The database id is an implementation detail.

---

# Performance

- Measure before optimizing.
- No N+1: relations come in the same query.
- Keyset (cursor) pagination, never offsets.
- Fetch only what is needed: use projections.
- Use indexes intentionally, for the filters and sorts an endpoint is built for.
- Use batches for many rows.

---

# Testing

Persistence is tested against a real PostgreSQL with the real migrations, never with mocked
accesses. The [test kit](/technical/components/persistence/) asserts what the code does:

```kotlin
val result = harness.execute { matchService.getMatch(created.id) }
result.assertSuccessful().assertQueryCount(2)
```

See [Testing](/development/06-testing/).

---

# Do's

✅ Declare persistence on the entity with the stratastax-entity annotations.

✅ Use the generated accesses for CRUD and relations.

✅ Keep SQL out of the rules.

✅ Use projections for lighter views.

✅ Use batches for many rows and cursors for large sets.

✅ Write reports as explicit, named queries.

✅ Assert query counts in tests.

---

# Don'ts

❌ Put business logic in an access or a mapper.

❌ Hand-write mappers or accesses the generator can produce.

❌ Edit generated code.

❌ Expose database ids.

❌ Load an entire table to compute a number.

❌ Call external systems inside a transaction.

❌ Mock the database.

❌ Change a migration that already ran.

---

# AI Agent Guidelines

When generating persistence code, AI assistants **must** follow these rules.

## Architecture

- Add or change the annotations on the entity; regenerate; never write the generated parts by hand.
- Put schema changes in a new migration in stratastax-contract.
- Keep the rules free of persistence types.

## Query Selection

| Situation | Preferred solution |
|-----------|--------------------|
| CRUD | The generated accesses |
| Search | `findAll` with a search request or the query DSL |
| Lighter view | A projection |
| Reporting | A named jOOQ query |
| Bulk | `createAll`, `updateAll`, `deleteAll` |

## Code Style

Generated and hand-written code alike should be explicit, readable, immutable where possible, easy
to test and free from framework magic.

---

# Summary

The persistence layer exists to store and retrieve data.

It is **not** the domain.

It is **not** the API.

It is **not** the business layer.

Declare it once on the entity, let it be generated, keep SQL out of the rules, and optimize only
where measurements demonstrate the need.
